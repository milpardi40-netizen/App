# گزارش استفاده از آپدیت‌ها — بخش تازهٔ Admin App

تاریخ: ۲۶ نوامبر ۲۰۲۶

## وضعیت تحویل

**قابلیت در کد پیاده‌سازی و آزمایش شده است؛ هنوز روی سرور اصلی فعال نشده و APK جدید ساخته نشده است.**

مطابق انتخاب «ترکیبی»، دو نوع اطلاعات کنار هم، ولی جدا و با برچسب روشن نمایش داده می‌شوند:

1. اطلاعات فعلی و قبلیِ موجود در فهرست انتشار و پروفایل کاربران.
2. رویدادهای دقیق‌تر از زمان فعال‌شدن ثبت روی سرور و نصب نسخهٔ مجهز به این قابلیت.

مسیر تازه: **Admin App ← بیشتر ← گزارش استفاده از آپدیت‌ها**؛ در نمایشگر عریض، از نوار کناری نیز در دسترس است.

## چه چیزی نمایش داده می‌شود؟

### نسخه‌ها

- نام اپ، شناسهٔ بسته، نام نسخه و شمارهٔ ساخت؛ بسته‌های متفاوت با شمارهٔ ساخت برابر با هم جمع نمی‌شوند.
- وضعیت انتشار فعال/غیرفعال، تاریخ انتشار ثبت‌شده و یادداشت انتشار.
- نسخه‌های بایگانی‌شده، حتی پس از حذف از فهرست انتشار، از زمان راه‌اندازی بایگانی.
- نسخه‌هایی که کاربر از بیرون برنامه نصب کرده و اجرای آن‌ها گزارش شده، حتی اگر در فهرست انتشار ثبت نشده باشند.
- کاربران دارای نشست، تعداد نشست‌های گزارش‌شده، دانلودهای درون‌برنامه‌ایِ تأییدشده، درخواست‌های نصب‌کننده و مشاهدهٔ اجرای نسخهٔ بالاتر.
- زمان اولین و آخرین دریافت گزارش توسط سرور.

هر نسخه دکمهٔ «کاربران و جزئیات این نسخه» دارد. فهرست‌ها صفحه‌بندیِ ۵۰ردیفی دارند؛ مجموع از سرور محاسبه می‌شود، نه فقط از صفحهٔ فعلی.

### کاربران هر نسخه و جزئیات رویداد

- نام و ایمیل در صورت وجود، شناسهٔ حساب، تعداد رویدادهای هر نوع و اولین/آخرین دریافت.
- آخرین شمارهٔ ساختِ دارای نشست برای همان اپ، با برچسب «آخرین مشاهده»؛ این مقدار تضمینِ نسخهٔ نصب‌شدهٔ فعلی روی همهٔ دستگاه‌های کاربر نیست.
- جست‌وجوی نام، ایمیل و شناسهٔ حساب.
- نمایش رویدادهای هر کاربر، همراه نوع، زمان اعلام‌شدهٔ دستگاه، زمان دریافت سرور و شناسهٔ رویداد؛ با صفحه‌بندی جداگانه.

حسابِ بدون پروفایل نام‌دار با شناسه نشان داده می‌شود؛ نام یا ایمیل ساختگی تولید نمی‌شود. یک حساب، به‌ویژه حسابِ دستگاه، لزوماً معادل یک شخص یکتا نیست.

### اطلاعات قبلی

زبانهٔ جداگانه، آخرین نسخهٔ گزارش‌شدهٔ پروفایل، نام، ایمیل، بستر و آخرین فعالیت موجود را نشان می‌دهد.

در دادهٔ قبلی شناسهٔ بستهٔ اپ و شمار دفعات استفاده وجود ندارد؛ بنابراین آن‌ها **نامشخص** هستند. کاربر صرفاً بر پایهٔ شمارهٔ نسخه به یک اپ مشخص نسبت داده نمی‌شود و اطلاعات فعلی به‌عنوان تاریخچهٔ کامل نمایش داده نمی‌شود.

## تعریف شمارنده‌ها

| عنوان | چیزی که واقعاً شمرده می‌شود |
|---|---|
| نشست استفاده | شروع سرد برنامه، یا بازگشت پس از حداقل ۳۰ دقیقه در پس‌زمینه، با حساب موجود |
| دانلود تأییدشده | دانلود داخل اپ پس از دریافت کامل و تأیید APK توسط کنترل‌کنندهٔ موجود |
| درخواست نصب‌کننده | درخواست بازکردن نصب‌کنندهٔ اندروید؛ **نه نصب موفق** |
| مشاهدهٔ ارتقا | مشاهدهٔ اجرای شمارهٔ ساخت بالاتر از شمارهٔ قبلاً ثبت‌شده برای همان حساب و بسته |
| کاربران دارای نشست | تعداد شناسه‌های حسابِ متمایز دارای رویداد نشست برای همان بسته/نسخه |

نصب اول با «ارتقا» یکی فرض نمی‌شود. رویدادها گزارش فنیِ کلاینت هستند، نه گواهی ضدتقلب یا تأیید نصب از فروشگاه/اندروید. زمان دستگاه نیز از زمان دریافت سرور جداست.

عدد صفر در شمارنده‌ها فقط یعنی **رویدادی دریافت نشده**، نه اینکه آن نسخه هیچ استفاده‌ای نداشته است. گذشتهٔ ثبت‌نشده قابل بازسازی نیست.

## چه چیزهایی دست‌نخورده ماندند؟

- صفحهٔ فعلی «به‌روزرسانی اپ‌ها» و همهٔ قابلیت‌های انتشار، حذف و ویرایش آن.
- صفحه‌های فعلی Admin App، ترتیب نسبی بخش‌های قبلی و محتوای آن‌ها؛ فقط یک ورودی تازه به منو اضافه شده است.
- ظاهر و محتوای آموزشی اپ کاربران، جمله‌ها، درس‌ها، مرحله‌ها و واژه‌آموزی.
- کنترل‌های امنیت فایل APK، منطق نصب و داده‌های پیشرفت.

در سه فایل موجود، جمعاً فقط **۷ خط اتصال افزوده** شده است: شروع ثبت فنی در ریشهٔ برنامه، دو نقطهٔ ثبت در مسیر دانلود/درخواست نصب، و یک گزینهٔ منوی مدیر. آزمون حفاظتی، **۲۲۸ فایل موجود** را با نسخهٔ قبل مقایسه می‌کند؛ تنها همین اتصال‌ها استثنا هستند.

تغییر اپ کاربران فقط ثبت فنیِ محدود است. پنجره، درس یا مرحلهٔ جدیدی به تجربهٔ زبان‌آموز اضافه نشده است. دادهٔ آموزشی، محتوای گفتگو، موقعیت مکانی، مخاطبان یا اثرانگشت دستگاه ارسال نمی‌شود.

## امنیت و ارتباط نامطمئن

- هیچ حساب تازه‌ای صرفاً برای شمارش ساخته نمی‌شود؛ بدون نشست احراز هویت، گزارشی ارسال نمی‌شود.
- حساب مدیر از نشست جداگانهٔ موجودِ Admin App استفاده می‌کند؛ نشست زبان‌آموز جایگزین آن نمی‌شود.
- سرور مالک رویداد را با `auth.uid()` تطبیق می‌دهد. عوض‌شدن حساب هنگام ارسالِ گزارشِ صف‌شده، رویداد را به حساب جدید نسبت نمی‌دهد.
- شناسهٔ ثابت رویداد در ارسال مجدد حفظ می‌شود؛ سرور تکرار آن را دوباره نمی‌شمارد.
- جدول‌ها دسترسی مستقیم عمومی یا کاربری ندارند؛ خواندن گزارش فقط با توابع دارای کنترل نقش مدیر انجام می‌شود.
- محدودیت نرخ برای هر حساب وجود دارد. نام بسته و نوع رویداد محدود و زمان اعلام‌شده اعتبارسنجی می‌شود.
- حداکثر ۵۰۰ رویدادِ محلی نگهداری می‌شود؛ رویدادهای بیش از ۹۰ روز کنار گذاشته می‌شوند. هر نوبت ارسال حداکثر ۲۵ رویداد دارد و بازگشت به برنامه/تغییر نشست/رویداد تازه، تلاش مجدد را فعال می‌کند.
- خرابی شبکه یا آماده‌نبودن سرور، درس و نصب را مسدود نمی‌کند. صف‌ها فقط با حساب مالک خود ارسال می‌شوند.
- حذف حساب در سرور، رویدادهای شناسایی‌پذیر آن حساب را نیز به‌صورت آبشاری حذف می‌کند.

بنابراین این گزارش **آمار دریافت‌شده** است، نه شمارندهٔ تضمین‌شدهٔ تمام استفاده‌های آفلاین، کاربران بدون حساب یا دانلودهای بیرون اپ. سیاست حریم خصوصی و اطلاع‌رسانی محصول باید این ثبت فنی را پیش از انتشار عمومی پوشش دهد.

## فعال‌سازی واقعی

### ۱. راه‌اندازی سرور

فایل زیر در SQL Editor پروژهٔ فعلی، توسط مسئول مجاز سرور، یک بار اجرا شود:

`supabase/SETUP-UPDATE-REPORTS-ONCE.sql`

همان migration نیز در این مسیر موجود است:

`supabase/migrations/202611260001_update_reports.sql`

فایل به راه‌اندازی‌های موجودِ مدیر، پروفایل کاربر/حساب دستگاه و انتشار اپ وابسته است. بازاجرای آن داده‌ها را پاک نمی‌کند. جدول و توابع تازه، بایگانیِ افزایشی انتشارها و دسترسی‌های محدود اضافه می‌شوند؛ ساختار محتوای آموزشی تغییر نمی‌کند.

**این فایل در این جلسه فقط در پایگاه دادهٔ آزمایشی اجرا شده است، نه روی Supabase اصلی.** در نبود راه‌اندازی، صفحه پیام روشن و مسیر همین فایل را نشان می‌دهد؛ آمار موفق یا صفرِ جعلی نمایش نمی‌دهد.

### ۲. نسخهٔ جدید Admin App

باید از این کد APK مدیر ساخته و نصب شود تا بخش تازه دیده شود. بخش قبلی انتشار به‌روزرسانی‌ها همچنان در جای خود است.

### ۳. فعال‌شدن شمارش در اپ کاربران

برای ثبت نشست‌ها و رویدادهای جدید، کاربران باید نسخهٔ مجهز به این کد را نصب کنند. **با نصب Admin App به‌تنهایی نمی‌توان از APKهای قدیمی شمارندهٔ استفاده دریافت کرد.** نسخهٔ شش‌زبانهٔ قبلی ۱۸۲ هنوز این ثبت فنی را ندارد.

انتخاب ساخت نسخهٔ تازهٔ اپ کاربران، زمان انتشار و دامنهٔ زبان‌ها باید جداگانه انجام شود؛ در این نوبت هیچ APK یا انتشار جدیدی انجام نشده است.

## آزمایش‌ها

همهٔ ۱۰ فرمان زیر موفق بودند:

```text
npm run validate:update-reports
npm run validate:apk-download
npm run validate:registration-admin
npm run validate:admin
npm run validate:russian-prea1-integration
npm run validate:word-lab
npm run validate:learner-controls
npm run validate:level-resume
npm run validate:operator-speech
npm run typecheck
```

فرمان اختصاصی گزارش شامل چهار بخش است:

1. محافظ دامنهٔ تغییر در ۲۲۸ فایل موجود.
2. اجرای واقعی SQL با PGlite: اجرای دوبارهٔ migration، نقش مهمان/کاربر/مدیر، جلوگیری از جعل مالک، تکرار رویداد، تفکیک بسته‌ها، جمع‌ها، جست‌وجو، صفحه‌بندی، محدودیت نرخ، بایگانی پس از حذف نسخه و حذف دادهٔ حساب.
3. منطق واقعی ثبت کلاینت: تکرار هم‌زمان نشست، تغییر حساب، صف آفلاین، ارتقا، انقضا، حد صف، بازگشت از پس‌زمینه، نشست مدیر و عدم اجرا روی وب.
4. رندر صفحه و اجزای واقعی گزارش با مرز شبیه‌سازی‌شدهٔ نمای بومی/نشست: ورود به نسخه، کاربر و رویداد، جست‌وجو، صفحه‌بندی، حالت خالی و خطای راه‌اندازی.

آزمون موجودِ دانلود نیز بررسی می‌کند فایل ردشده رویداد دانلودِ تأییدشده یا درخواست نصب تولید نکند.

خروجی وبِ Admin App با مسیر `/admin/update-reports` نیز ساخته شد (`dist/update-reports-admin`). فرمان اولیه از محدودیت زمانی ابزار عبور کرد؛ همان فرایند بدون اجرای مجدد تا پیام `Exported` ادامه یافت و وجود فایل صفحه بررسی شد. خروجی تولیدشده وارد Git نمی‌شود.

`git diff --check` موفق بود. گزارش نتایج: `reports/update-report-validation.json`.

آزمون روی گوشی واقعی، ترافیک واقعی Supabase و دادهٔ حساب‌های واقعی انجام نشده است. هشدار منسوخ‌شدن React Test Renderer و قدیمی‌بودن دادهٔ Browserslist مانع موفقیت بررسی‌ها نبودند.

**APK، commit، push یا تغییر سرور اصلی در این نوبت انجام نشده است.**
